# Feature: маршруты, каскады, failover

> **Реализация 0.7.0-stage5-foundation:** существует только сохранение и симуляция черновиков RoutePolicy (SQLite/API/React). Xray outbound/inbound, межнодовые ключи, реальный failover и публикация отсутствуют. Полный список задач — [stage5-checklist](../planning/stage5-checklist.md). Ниже **целевая** спецификация, а не готовые функции.

## Редактор черновиков — 2026-11-05

Реализованы схема React Flow и таблица с общей формой: direct/cascade, основной выход, до четырёх упорядоченных резервов. Соединение карточек меняет только форму; нужно отдельно сохранить черновик. Preview показывает before/after и сбрасывается при изменении ввода. Сохранение конфликта версий не перезаписывает чужие правки. На мобильном таблица открывается по умолчанию; все действия доступны без drag-and-drop.

Зависимая нода не может быть отозвана или поставлена в SSH purge/detach: HTTP 409 перечисляет маршруты. После начала удаления запрещено добавлять эту ноду в новые/изменяемые черновики. Сохранение `backup_exits` всегда возвращает массив, включая пустой.

Черновики переносятся в encrypted backup v4; старые форматы сохраняют текущие маршруты и отклоняются при разрыве ссылок на ноды. Подробнее: [блок изменений](../release-0.7.0-stage5-routing-ui.md), [ADR-004](../adr/004-draft-routing-editor-and-backup.md).

## Конфигурация из UI

- `Direct`: клиент → выбранный VPS → интернет.
- `Cascade`: клиент → вход A → выход B → интернет.
- `Cascade + fallback exit`: клиент → A → B (основной) или C (резервный) → интернет.
- `Rules`: выбор egress по domain/IP/GeoIP/Geosite при поддержке движка.

Роли не связаны со страной: NL→RU так же корректен, как RU→NL. Нельзя автоматически назначать роли по региону.

## Безопасное применение

1. Проверить, что вход и выход различимы и граф маршрутов не содержит циклов.
2. Создать отдельные credentials межсерверного канала.
3. Подготовить правило Inbound на выходе/Outbound на входе и firewall.
4. Применить только после успешной проверки промежуточных зависимостей.
5. Сделать egress probe и сравнить фактический exit IP с ожидаемым.
6. Только после успеха опубликовать активный маршрут.
7. При любой частичной ошибке показать per-node состояние и выполнить компенсационные операции.

## Failover

Probe должен подтверждать не только процесс и порт, но и конечный доступ через маршрут. Переключение после N failures, recovery после M successes и cooldown (значения определяются тестами). Fail-closed по умолчанию, fail-open только при явном согласии.

Исходные TCP/UDP-сессии могут оборваться. Нет гарантии бесшовного восстановления соединений. Для мёртвого входного IP нужен резервный клиентский профиль и поддержка переподключения на клиенте.
