# Feature: безопасная ОС и внешнее управление сервером из UI

**Статус:** требования, **не** гарантия безопасности. Настройки должны быть безопасными по умолчанию, но правомерность действий зависит от ОС, доступа и сценария. «Максимально безопасно» определяется моделью угроз и проверяемыми control/test cases, а не количеством включённых настроек.

## 1. Целевые свойства

- Не раскрывать публично API агента и Xray management API. Последний слушает loopback / локальный Unix socket, если поддерживается конкретной версией; сетевой доступ снаружи запрещён.
- Панель доступна только по проверяемому HTTPS; желательно ограничение по IP/administrative tunnel. Сервис подписок — отдельный endpoint с ограниченными capabilities, не тот же админ-токен.
- На каждом сервере минимум полномочий; системные действия выполняются allowlisted privileged helper под systemd/polkit/sudo с узкими правилами, а не shell API.
- Все изменения логируются безопасно; credentials и subscription tokens в логах не отображаются.
- Поддерживать последнюю исправную Xray-конфигурацию и резервные копии SQLite/секретов.

## 2. Firewall и сетевой периметр

- Для проверенных Ubuntu/Debian реализовать драйвер UFW; возможен отдельный драйвер nftables после тестов. Не смешивать управление несколькими firewall engines без определения источника истины.
- Драйвер строит *desired managed rules*, выполняет diff с фактическим состоянием; любые чужие правила — read-only до явного подтверждения администратора.
- Открытие порта: проверка владельца (Inbound/SSH/HTTPS/Agent), протокола TCP/UDP, IPv4/IPv6, bind address, конфликтов и состояния облачного firewall. После UFW-success проверять внешний TCP/UDP путь доступными инструментами.
- Закрытие порта: разрешено только если **нет ни одного зависимого managed connection**. Удаление соединения не должно закрывать общий порт HTTPS/SSH.
- Firewall plan: новый порт до закрытия старого; scheduled rollback с локальным таймером **на VPS** и независимым подтверждением доступности управляющего доступа. Потеря browser session сама по себе не подтверждает откат.
- Установка firewall на VPS с Docker/Podman network требует явной проверки NAT / forwarding / host network: published container ports могут обходить ожидания UFW. По умолчанию systemd + host networking без контейнерных пробросов.
- Приложение не способно автоматически открыть облачный security group, если нет API-подключения к провайдеру: UI показывает, что локальное правило есть, но порт заблокирован извне.
- Без необходимости не менять sysctl, NAT, ip_forward и правила других сервисов.

## 3. SSH hardening

- Предпочитать ключи; пароль допустим для bootstrap по явному выбору, без хранения.
- Проверить реальный альтернативный вход **новым SSH-сеансом** до отключения root/password/старого порта.
- Не блокировать доступ пользователю, если машина доступна только по единственному критическому каналу. Предупреждать об отсутствии provider console/rescue.
- Ограничения SSH по IP, AllowUsers, MaxAuthTries, время ожидания и rate limiting — только с учётом текущей ОС, конфликта существующих политик и проверенного rollback.
- Ротация host key при переносе VPS должна быть отображена; нельзя молча доверять подменённому серверу.
- Не отображать «SSH защищён» без явных проверенных критериев.

## 4. HTTPS и сертификаты

- Поддерживать проверяемый сертификат на публичный IP без обязательного домена (ACME-клиент должен действительно поддерживать IP identifiers и выбранный challenge).
- Let's Encrypt с 2026 года выдаёт сертификаты IP сроком 160 часов. Нужны автоматическое продление задолго до expiry, мониторинг, алерт, резервный план и тест после reload. Короткий срок — не недостаток проекта, но это критическая эксплуатационная зависимость.
- Условия challenge могут требовать доступности определённых портов; preflight должен проверить фактическую поддержку провайдера и выбранного метода.
- Не допускать `insecure_skip_verify` и «вечных» self-signed сертификатов как скрытого обходного пути. Для закрытого контура альтернативой может быть явно установленный trust anchor/pinning с отдельным UX.
- Разделять TLS панели, подписок, mTLS агентов и VPN-транспорт Reality: это разные системы ключей и назначений.
- **Один публичный IP и порт 443:** панель HTTPS и Xray Inbound не могут независимо занять одинаковые IP:port/transport одновременно. При standalone wizard должен выявить конфликт и предложить отдельный порт HTTPS, другой bind-address или отдельно проверенную схему мультиплексирования; нельзя молча останавливать работающий VPN. ACME challenge/renewal при этом должен быть явно совместим с выбранными портами.
- Отсутствие домена не гарантирует незаметность IP или VPN-трафика; это исключительно выбор сетевого имени.

## 5. Identity и секреты

- Root CA и ключи signing: хранение с правами ОС, шифрование при экспорте, резервирование, ротация и отзыв. Не делать общий mTLS-сертификат для всей fleet.
- Генерация через криптографически стойкий источник случайности; отдельные credentials для клиента/ноды/каскадного канала.
- Подписка — bearer URL; поддержать замену токена, expiry/отзыв, rate limiting; не писать полный токен в access logs.
- Защищать хранимые секреты ключом, который не хранится в той же SQLite как открытый текст. Утрата master key без backup делает восстановление зашифрованных секретов невозможным — показывать это оператору.
- Управляющие команды: строгие DTO, authorization, expected revision, nonce/anti-replay, bounded deadlines, audit.

## 6. Хост и процесс

- systemd units: dedicated users, корректные `ProtectSystem`, `NoNewPrivileges`, capabilities и ограничения путей (после доказанной совместимости); root нужен только узким операциям.
- Агент не получает возможность произвольной загрузки и выполнения команд. Обновления — только подписанные/проверенные артефакты конкретной версии.
- Системные патчи: осознанная политика install/restart, предупреждение о потенциальных перерывах VPN, осторожное staged rollout.
- Можно предложить базовую защиту от перебора и автоматическую ротацию логов, но не добавлять тяжёлую постоянно работающую систему ради декоративного «security score».
- Не обещать отсутствие сетевых утечек на клиентском устройстве без контроля его VPN-клиента, DNS и OS kill-switch.

## 7. UI: «Безопасность сервера»

Табы: **Состояние | Firewall | SSH | HTTPS | Сервисы | Обновления | Аудит**.

Каждая настройка: текущий факт, рекомендация, управляется ли панелью, ожидаемое изменение, возможность отмены. Для критических операций — diff и окно подтверждения. Статусы `проверено`, `рекомендуется`, `невозможно проверить`, `ошибка`; избегать имитации «100% защищённости».

## 8. Обязательные security tests

1. Попытка «открыть произвольный localhost/metadata» через установщик блокируется правилами SSRF.
2. SSH host key mismatch без подтверждения не продолжает bootstrap.
3. Некорректный UFW/SSH rollout не разрывает единственный доступ при доступной rollback-механике.
4. Сбой внешнего cloud firewall не отмечается как «порт открыт».
5. mTLS revoked node не может получать дальнейшие команды.
6. Ошибочная Xray-конфигурация не заменяет last-good.
7. Подписки и SSH-секреты не попадают в логи и API ошибок.
8. Admin HTTP API проверяет права, CSRF, активность сессии, лимиты запросов.
9. TLS certificate renewal реальным client validation проходит, до срока истечения работает алерт.
10. Частичный сбой восстановления резервной копии не выдаётся за успешное восстановление.
