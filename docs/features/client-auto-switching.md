# Автопереключение протокола и входного сервера

Дата: 2026-11-05. Статус: требование пользователя и проектный контракт; runtime и экспорт клиенту **не реализованы**, работоспособность Happ не подтверждена. Это не failover серверного каскада из `internal/routes` и не новая VPN-технология.

## Ответственность

При недоступном входном VPS переключение делает клиент устройства. Агент на VPS и панель видят другую сеть и не могут достоверно определить, доступен ли VLESS/Hysteria2 из сети конкретного пользователя. Нужны заранее полученные клиентом разрешённые альтернативы; панель не должна быть обязательна для переключения. Если текущая нода продолжает принимать вход, отдельно возможна смена выхода каскада; она сохраняет stage5 ACK/egress/publish gates.

Кандидат — конкретная пара «логический сервер + профиль протокола», с собственными адресом, credentials, TLS-настройками, областью маршрутизации и поддержкой клиента. Xray-профиль VLESS и Hysteria2 нельзя автоматически считать поддерживаемыми одним клиентским движком. WireGuard/AWG не добавляются в клиентскую группу без проверки соответствующего runtime/ОС.

## Алгоритм

1. Во время работы редко проверять активное подключение и ограниченный набор резервов; при старте, ошибке или смене Wi-Fi/мобильной сети запускать ограниченный **параллельный раунд** всех разрешённых кандидатов. Ограничить одновременные соединения, частоту, время и объём, отменять устаревшие раунды; jitter/backoff и сон в простое экономят батарею/трафик. Пределы проверяются на целевом клиенте.
2. Проба выполняет реальный запрос **через конкретный кандидат** с его аутентификацией и проверкой TLS. TCP к открытому порту, ping IP, heartbeat агента и TLS-проба чужого SNI сами по себе не доказывают работу туннеля. Не использовать пользовательские запросы и не дублировать POST/платежи; только отдельные ограниченные идемпотентные пробы.
3. Различать `healthy / failed / unknown / stale / unsupported`; замер привязан к кандидату, сетевому контексту и времени. Не считать непроверенный резерв рабочим. Отдельно проверять две независимые контрольные HTTPS-цели: отказ одного сайта или DNS-источника не означает отказ всего VPN. Ошибка проверки сертификата не разрешает TLS bypass.
4. Стартовое проектное правило по запросу пользователя — **два последовательных неуспешных раунда** для активного кандидата; порог и интервалы доступны в расширенных настройках и ещё требуют испытаний. После порога сначала выбрать уже проверенный рабочий протокол **того же сервера**. Если все разрешённые профили этого сервера достигли порога отказа, выбрать рабочий кандидат другого разрешённого сервера. Не обходить серверы последовательной цепочкой таймаутов: результаты резервов собираются тем же параллельным раундом. Нельзя обещать гарантированное время переключения без фиксированных лимитов и измерений.
5. Выбор среди рабочих: приоритет пользователя, свежесть/доля успехов, затем задержка. Не прыгать на чуть меньший ping при исправном активном подключении. После смены — cooldown/минимальное время удержания; возврат к основному только после нескольких успешных проб и по включённой политике возврата. Отказ уже выбранного резерва запускает ту же процедуру. Параллельные пробы не означают параллельную передачу пользовательских данных или балансировку каждой сессии.
6. Если все кандидаты отказали или нет сети — состояние «Нет доступного подключения», редкие повторные проверки, сохранение kill-switch/fail-closed. Никакого автоматического прямого выхода. Диагностика отсутствия интернета ограничена системным состоянием интерфейса и отдельно документированным контрольным механизмом; не добавлять скрытые direct-запросы.
7. При смене egress IP/туннеля существующие TCP/QUIC-сессии могут оборваться; приложение переподключается. Не обещать бесшовное сохранение звонка/загрузки. Реакция на существующие соединения зависит от клиента и проверяется отдельно.

## UI и клиентский контракт

- Необязательный тумблер «Автопереключение», выбор разрешённых серверов и протоколов, предпочтительного сервера; базовый режим «Сначала другой протокол этого сервера, затем резервный сервер».
- «Дополнительно»: число неудач/успехов, interval/timeout, concurrency, cooldown, ручной приоритет, политика возврата. До применения — поддерживаемый клиент/версия/ОС и diff. Несовместимая комбинация заблокирована с причиной.
- Показать, **кто** переключает: клиент или серверный каскад. Последняя смена, причина и свежесть только по реально доступной телеметрии; не показывать клиентское состояние на основании heartbeat VPS.
- Не обходить клиентские ограничения JSON-подписок ради одновременно обещанного редактируемого Happ routing. Способ объединения пользовательских правил и авто-группы требует отдельной проверки клиента. Не выдавать обычный список `vless://`/`hysteria2://` за управляющую политику автоматического переключения.

## Подтверждённые строительные блоки и ограничения

- [Xray observatory](https://xtls.github.io/en/config/observatory.html) умеет проверять outbound HTTPing; `enableConcurrency=true` запускает пробы одновременно. [Balancer](https://xtls.github.io/en/config/routing.html) использует observatory для `leastPing`/`leastLoad`. При отсутствии доступных кандидатов возможен default outbound: генератор обязан явно обеспечивать fail-closed. Это не готовая реализация двухуровневого протокольного failover с указанными порогами.
- [sing-box URLTest](https://sing-box.sagernet.org/configuration/outbound/urltest/) имеет interval/tolerance и политику прерывания соединений; это строительный блок, а не доказательство всего алгоритма и совместимости Happ.
- [Официальный Happ routing](https://www.happ.su/main/ru/dev-docs/routing.md) описывает ограничения provider JSON и применение после reconnect; прочитанная документация не подтверждает всю требуемую матрицу VLESS/Hysteria2/ОС. Перед выпуском выбрать закреплённые версии клиентов и подтвердить импорт/поведение на реальном устройстве. Серверный Go-процесс не заменяет клиентский контроллер.

Источники проверены 2026-11-05. Приёмка: заблокировать UDP, затем TCP, затем IP входного VPS; отдельно отказ одного контрольного сайта, отсутствие интернета, DNS/TLS-ошибка, частичные потери, recovery/flapping, переход сети и сон телефона. Независимо подтвердить протокол, exit IP, DNS/IPv6 и отсутствие direct-утечек. До этого возможны только проектирование и локальные модели, без статуса «автопереключение работает».


## Уточнение 2026-11-06: стандартные клиенты

Пользователь выбрал Happ, Streisand и другие стандартные приложения, без собственного клиента. Обычные URI/подписки остаются базовым контрактом. [Happ app-management](https://github.com/HappDev/happ_su/blob/main/dev-docs/app-management.md) описывает auto-ping при открытии и autoconnect lowestdelay с Provider ID; это не документированная гарантия непрерывного двухуровневого parallel failover. JSON passthrough [ограничивает родной routing UI](https://github.com/HappDev/happ_su/blob/main/dev-docs/examples-of-links-and-parameters.md), его нельзя незаметно включать по умолчанию. [Streisand App Store](https://apps.apple.com/us/app/streisand/id6450534064) заявляет VLESS/REALITY/HysteriaV2/WireGuard, но не подтверждает требуемый алгоритм/пороги. Реальные устройства и импорт не тестировались; неизвестная возможность остаётся unsupported, а не выдуманным полем URI. Подключение по отдельному URI и QR реализовано независимо: [контракт](direct-client-access.md).
