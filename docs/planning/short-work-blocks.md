# Короткие рабочие блоки и достаточные проверки

Согласовано 2026-11-06. Цель — быстро получать конкретный проверяемый результат, без часовых циклов подготовки и повторных неизменённых прогонов.

## Обычный блок

1. Зафиксировать одну задачу и измеримый результат. Ориентир — 10–15 минут; большой объём разбить до начала, не наращивать его по ходу.
2. Прочитать текущую задачу и затронутый модуль. Не проводить новый полный аудит проекта перед каждой правкой.
3. Написать минимальный полный код или документацию. Не создавать вспомогательные скрипты, снимки окружения и новые абстракции без необходимости.
4. Выполнить минимальные достаточные проверки затронутых контрактов. Исправить вызванные изменением ошибки.
5. Обновить текущую задачу и документацию. При разрешённой отправке — коммит/push и краткий отчёт: что готово, что проверено, что осталось.

## Выбор проверок

| Изменение | Обычный минимум |
|---|---|
| README/план/документация | Ссылки, команды по исходникам, diff/согласованность; без Go/frontend сборок |
| Установочные/build shell-скрипты | `bash -n`, целевой disposable fixture без изменения ОС |
| Локальная бизнес-логика | Тесты затронутого пакета/контракта; build/vet по необходимости |
| UI | TypeScript/build и один целевой сценарий; широкая browser-матрица только при изменении layout/общих компонентов |
| Credentials, права, БД, rollback | Целевые security/transaction regression обязательны; непроверенный runtime отдельно отмечается |
| Выпуск релиза | Отдельный согласованный блок: полный набор release checks, сборка, подпись и внешняя приёмка |

Не запускать по умолчанию полный `go test -race ./...`, повторные `npm ci`, все размеры/темы/E2E, контейнерные стенды и real VPN tests после каждой мелкой правки. Не повторять PASS, пока его inputs не менялись. После исправления повторять затронутую проверку, не весь проект.

Если необходимая проверка долгая или требует VM/VPS, назвать причину и выделить отдельный блок приёмки. Не подменять её симуляцией и не отмечать PASS. Ошибки, проверки безопасности, подписи, TLS/SSH validation и rollback не ослаблять ради времени. Новая полезная идея — следующий блок, не скрытое расширение текущего.

## Поддержание публичной документации

При изменении доступных возможностей, требований, установки или обновления в том же коммите обновлять README и `docs/ops/install-and-update.md`. Проверять имена файлов/CLI по исходникам. README должен показывать текущее состояние для нового человека; исторические статусы остаются в release/testing документах. Не обещать отсутствующий GitHub Release, платформу, автоматическую миграцию или неподтверждённую production readiness.
