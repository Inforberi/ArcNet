Для каждого этапа различать `LOCAL_PASS` (всё доступное локально проверено) и `ACCEPTED` (получены необходимые внешние доказательства). См. ## Порядок работы

1. Полностью реализовать **кодовую часть** этапа и убрать демонстрационные элементы, выдаваемые за рабочие действия.
2. Выполнить доступные локальные проверки и сохранить команды/вывод (без утверждений о том, что не запускалось).
3. Если проверка требует внешней среды, оформить точное воспроизводимое задание Codex с версией коммита, ожидаемым результатом и rollback.
4. При `LOCAL_PASS / EXTERNAL_PENDING` разрешается продолжать **разработку** следующего этапа, но предыдущий этап остаётся *не принятым*, и production-релиз запрещён. Это не считается «сдачей частичного этапа».
5. При внешней ошибке исправить код, повторить локальные проверки, после чего заново выполнить внешнюю приёмку. `ACCEPTED` — только после всех обязательных доказательств.

## Границы продукта

- Полноценный режим одного сервера без каскада обязателен; удалённые VPS и каскады — опциональные возможности.
- Автоматическое переключение **выходного маршрута** не гарантирует сохранение существующих TCP-сессий. Переключение **входа/протокола пользователя** возможно лишь при реальной поддержке используемого клиента; один серверный ping недостаточен.
- Интеграцию импорта **из 3x-ui исключили**. Нужен полный перенос **ArcVPN → ArcVPN** через зашифрованный архив из UI; сохранение URL при смене IP сервиса подписки не гарантируется.
- Не обещать «невозможность обнаружения», безотказность, отсутствие блокировок, установленный «лучший SNI» или подтверждённые 1 vCPU/1 ГБ до независимых измерений.
- Сравнивать протоколы по поддержке движков, безопасности настройки и клиентской совместимости; не запускать все движки по умолчанию.
