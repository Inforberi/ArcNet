# Подготовка к самостоятельной проверке на VPS

Решение пользователя, 2026-11-06: серверные испытания выполняет пользователь. Нужны установка одной командой и простое управление всей локальной установкой через `arcvpn`, включая запуск, остановку и перезапуск. Этот документ — **план**, а не подтверждение реализации команд или успешной установки.

**Продолжение A1:** CLI реализован в исходниках, targeted Linux tests/vet/race, Bash fixtures и diagnostic build прошли. [Контракт](../ops/local-service-control.md), [результаты](../testing/local-results/stage5-2026-11-06-local-lifecycle.md), [ADR-013](../adr/013-local-runtime-lifecycle.md). Настоящие systemd/VPS и полная миграция старой установки не приняты. Следующая кодовая подготовка — A2; общая установка одной командой ещё отсутствует.

## Фактическая исходная точка

- `scripts/build-release.sh` собирает Linux x86_64 core со встроенным React; `scripts/package-release.sh` формирует installer tar.gz. Полный выпуск/установка на VPS ещё не приняты. Source ZIP не заменяет установочный пакет.
- `install.sh` содержит проверки ОС/портов, systemd setup, IP ACME и установку runtime dependencies. Нет принятого готового сценария безопасной сетевой установки одной командой.
- `deploy/arcvpn-menu.sh` и `core lifecycle`: меню, recovery/settings, общие start/stop/restart/status, bounded logs и component restarts реализованы локально; для настоящего systemd нужны отдельные испытания и новая согласованная обвязка.
- Первое подключение TCP REALITY/XHTTP/Hysteria2/WireGuard не требует предварительного TCP REALITY: [ADR-012](../adr/012-independent-first-local-protocol.md). Локальный UI/API PASS не доказывает настоящий VPN.
- Каскады остаются редактором/симуляцией. Geo, реальный failover и распределённые лимиты не следует выдавать за доступные функции тестовой сборки.

## A. До передачи первой тестовой сборки пользователю

### A1. Полное управление локальной установкой одной командой

Команды ниже реализованы в исходниках A1 и доступны после установки нового согласованного core/wrapper/units. Это **не подтверждение работы на VPS**; точные ограничения — в CLI-контракте выше:

| Команда | Требуемое поведение |
|---|---|
| `sudo arcvpn` | Понятное меню; те же действия, что в CLI, без дублирования бизнес-логики |
| `sudo arcvpn start` | Запустить панель и настроенные включённые локальные VPN-службы |
| `sudo arcvpn stop` | Остановить панель и локальный VPN-runtime; сохранить конфигурации, пользователей и ключи |
| `sudo arcvpn restart` | Контролируемо перезапустить включённые компоненты и проверить итог каждого |
| `sudo arcvpn status` | Сводка панели, Xray, Hysteria2, WireGuard и нужных helpers: desired/actual/error |
| `sudo arcvpn logs` | Ограниченный вывод журналов ArcVPN с выбором компонента |
| `sudo arcvpn doctor` | Существующая базовая диагностика; полный prerequisites/ports/TLS preflight — A2/A3, службы/desired state — новый status |

Контракт реализации:

- Область команды — только эта локальная установка и известные ей службы/helpers. SSH, чужие службы, удалённые ноды и их VPN не останавливаются. Старые варианты `restart panel|xray` сохраняются; другие компоненты добавляются по строгой allowlist.
- `start/restart` не включают отключённые профили, не создают ненужные listeners и не ротируют credentials. Повторный `start/stop` идемпотентен. Отсутствующий необязательный движок — «не настроен», а не ошибка всей установки.
- Остановка сначала исключает новые управляющие операции и завершает worker/apply, затем корректно останавливает VPN и требуемые helpers. Запуск учитывает зависимости helpers/движков/панели. Прямой и обратный порядок нельзя заменить произвольным списком `systemctl`.
- По возможности снять финальные counters перед остановкой; неподтверждённый хвост/смена epoch отмечаются как неполные данные. Не обнулять расход или review gate ради успешного restart.
- TLS-renewal/backup timers и автозапуск после reboot имеют явно описанную отдельную политику. `stop` не означает uninstall или автоматическое отключение renewal. Фоновые hooks/reconcile не должны самовольно поднимать остановленный runtime; поведение после reboot явно показывается согласно настройке автозапуска.
- Обязательны lock/ограниченное ожидание, защита от параллельных lifecycle/apply/update, проверка результата каждого компонента и понятный partial failure. Отказ helper/движка не выдаётся за общий успех; сохраняются last-good конфигурации и путь восстановления.
- Нужны стабильные exit codes и безопасный машинный status для тестирования; неизвестный unit/лишний аргумент отклоняется. Логи ограничены по объёму и не раскрывают секреты.
- До root-изменений актуализировать [модель угроз](../security/threat-model.md). Локально проверить порядок/идемпотентность/отказы allowlisted fixture; реальный systemd/rollback проверит пользователь на изолированном тестовом VPS по отдельному сценарию. До этого runtime остаётся непроверенным.

**Готовность A1:** одна команда действительно управляет всем заявленным локальным runtime, состояние каждого компонента видно; fixture не заменяет серверную проверку.

### A2. Воспроизводимый тестовый пакет

- Выполнить Linux x86_64 release build со встроенным UI и достаточными release checks. Зафиксировать commit/version, состав, зависимости и поддержанные цели, не обещать непроверенную ABI-совместимость с любой ОС.
- Проверить наличие и права core, wrapper/helpers, units и нужных runtime-компонентов. Node.js/Go/npm нужны машине сборки, на VPS сборки исходников не требуется.
- Подготовить installer asset и проверяемый подписанный манифест. Зафиксировать происхождение доверенного ключа независимо от скачиваемого payload. SHA256 из того же неподтверждённого источника — только контроль повреждения.
- Подготовить инструкцию обновления wrappers/helpers/units и БД: нынешний core-only updater не мигрирует всю ОС-обвязку. Откат одного core не считается откатом миграции БД или unit-файлов.
- Публикация тестового пакета/Release — отдельное явно разрешённое действие, только после подготовки и проверок. Не путать её с уже разрешённым push исходников.

**Готовность A2:** пакет можно установить без dev environment; все заявленные файлы, версии и проверки отражены в release notes. Он обозначен как тестовый до приёмки пользователя.

### A3. Установка одной командой

- Сделать небольшой bootstrap для закреплённого тестового релиза: скачать → проверить происхождение/подпись и hash → безопасно распаковать → вызвать проверенный installer.
- Не исполнять непроверенный сетевой payload от root. Однострочный запуск не должен скрывать отсутствие доверенного ключа или заменять независимую проверку скачиванием hash рядом с архивом.
- Проверка до root-исполнения относится и к самому bootstrap, а не только к скачанному им архиву. Доверенный pin/ключ доставляется независимо от проверяемого сетевого содержимого; точный способ фиксируется перед реализацией.
- Итоговую копируемую команду с настоящими URL/версией выдавать только после наличия проверенного asset; не публиковать сейчас фиктивный `curl | bash`.
- Автоматически проверить ОС/архитектуру/systemd, зависимости, выбранные порты, доступ к ACME и существующую установку. При конфликте — понятный отказ до изменений; повторная установка не заменяет update.
- По умолчанию использовать публичный IP и короткоживущий IP-сертификат с контролем renewal. Домен — необязательный последующий сценарий с проверкой имени/сертификата и предупреждением об изменении ссылок. Отказ ACME не обходить отключением TLS.
- Настроить ограниченные журналы/retention и показать их бюджет. Секреты установки не передавать в argv; пароль администратора выдаётся локально, повторный запуск не сбрасывает его молча.
- Не менять SSH/UFW потенциально блокирующим образом без проверенного восстановления. Откатывать только ресурсы этой попытки; не удалять прежние пользовательские данные/службы.
- После установки показать URL панели, команду `arcvpn`, фактические состояния и следующий тест. `active` службы не подписывать как подтверждённое VPN-подключение.

**Готовность A3:** подготовлена настоящая однострочная команда для тестового пакета, локально пройдены проверки подписи/распаковки/preflight/failure cleanup. Факт установки на VPS подтвердит пользователь.

### A4. Передача пользователю сценария приёмки

Подготовить короткий checklist с ожидаемым результатом и диагностикой, без передачи паролей/ключей в чат:

1. Чистый тестовый VPS/консоль/snapshot, установка одной командой; записать ОС, RAM/CPU, версию/commit, результат ACME и служб.
2. Вход, 2FA, `settings`, сброс пароля с сохранением 2FA, отдельное восстановление утраченной 2FA.
3. По очереди первый TCP REALITY, XHTTP, Hysteria2 и WireGuard; независимый клиент, реальный внешний egress, DNS/TCP/UDP в применимых сценариях. Наличие ключа/ссылки не считается handshake.
4. `stop/start/restart/status`, повтор команд, отключённый профиль, перезагрузка, недоступный компонент и занятый порт. Проверить отсутствие случайного включения лишнего протокола.
5. Пользователь/устройство, расход, пакет/срок, фактический отзыв и время исполнения; restart/replay не списывают повторно. Пропуски не маскируются.
6. Backup v10/restore на чистую установку и при отказе apply; ключи/token сохраняются, уже известные расходы/отзывы не откатываются. Смена IP требует собственного сертификата и обновления клиентских ссылок.
7. TLS renewal, bounded logs/диск, signed update и восстановление. На контрольном профиле512МиБ/1vCPU измерить реальную память/CPU с используемыми движками; пока это не minimum.

Пользователю передаются установочная команда, checklist, допустимые команды диагностики и способ вернуть last-good/snapshot. PASS ставится только по фактическим результатам; непроверенные строки остаются NOT RUN.

## B. До полной проверки нод и каскадов

Эти функции можно не ждать для первой проверки установки/локальных протоколов, но нельзя заявлять их готовность или предлагать тестировать стрелочки как работающий каскад:

- LogicalEndpoint, отдельные межнодовые credentials и безопасные генераторы конфигураций входа/выхода.
- Подготовка выходов перед входом, typed apply/ACK всех нод, last-good, restart/reconcile и компенсация частичного отказа.
- Проверка настоящего клиентского пути/выходного IP, затем отдельная публикация подписки. Unknown/heartbeat не заменяют независимую egress-пробу.
- Remote device credentials/отзыв и общий пакет без двойного списания межнодового трафика.
- Только затем испытания A→B/B→A, отказа входа/выхода, 2–3 VPS и реального failover по [stage5 checklist](stage5-checklist.md).

GeoIP/GeoSite, применение пользовательских правил и клиентское параллельное переключение остаются отдельными блоками. Новые протоколы/stage6 и AmneziaWG не добавляются.

## Очередь коротких блоков

1. A1: CLI lifecycle и единая сводка реализованы локально; systemd-проверка пользователем остаётся открытой.
2. A2: release build/упаковка/доверенный манифест и инструкция миграции.
3. A3: проверенный bootstrap одной командой и локальные failure fixtures.
4. A4: пользовательская приёмка первого тестового VPS; исправления по её фактическим результатам.
5. B: реализация и отдельная многонодовая приёмка каскадов; остальные функции — последующими блоками.

Первоначальный блок менял только план. Продолжение A1 реализовало локальный CLI и перечисленные source/fixture проверки; installer asset/bootstrap и настоящие серверные испытания по-прежнему не завершены.
