# Простой первый сценарий ArcVPN

## Расход без истории и понятные устройства — дополнение 2026-11-07

По скриншотам пользователя: длинные «Последние списания» с одинаковыми нулевыми строками и абстрактное «Активные доступы устройств 0 / без лимита» не дают полезной информации. История удалена из исходников UI; доработка устройств остаётся требованием.

- Уточнение пользователя: историю списаний/трафика полностью убрать из UI, в том числе по запросу. Оставить расход, лимит, остаток и срок. Внутренний ledger/checkpoints сохранить для корректного исполнения пакетов.
- Не отображать действительно нулевые байтовые приращения как расход. Малый ненулевой объём показывать в Б/КБ/МБ/ГБ с принятой десятичной шкалой пакетов, чтобы округление не превращало реальный расход в «0 ГБ». Различать отсутствие расхода, отсутствие свежих данных и неполный учёт. Не удалять/пересчитывать ledger, checkpoints, события смены периода и известные списания ради чистоты UI; ограничить только представление и объём запрашиваемых деталей. Загрузка/ошибка/пустое состояние не превращаются в фиктивный ноль.
- Вместо одного счётчика показывать компактный список доступов с понятным именем (например, «iPhone Лёши», «Ноутбук»), доступными подключениями/протоколами, состоянием и последней активностью, а также лимитом и действиями «Подключить», «Переименовать», «Отозвать». Расход по устройству показывать только при достоверном per-device учёте; если доступен лишь общий расход пользователя — подписывать его именно так, без распределения по предположению. Создание имени/типа не должно становиться сложной обязательной первоначальной настройкой.
- Тип/ОС/приложение можно предлагать по реально доступным метаданным, с указанием источника/приблизительности и возможностью исправить имя. Загрузка подписки и её User-Agent не подтверждают активное VPN-соединение; fingerprint Chrome/Firefox не доказывает фактический браузер/ОС. Не обещать автоматическое определение модели телефона или MAC по обычному VLESS. Если сведений нет, показывать понятное нейтральное название и «Нет данных», а не выдуманную модель.
- Разделить «выдан доступ», «была активность» и «онлайн»: последний требует свежего подтверждения с определённым окном актуальности, не равен enabled credential. Общий UUID/ключ не позволяет надёжно посчитать физические устройства. Для legacy общего доступа показывать строку «Общий профиль» и пояснение ограниченной идентификации вместо вводящего в заблуждение «0 устройств». Существующий общий ключ не отзывать скрыто; переход к индивидуальным доступам — отдельный понятный подтверждаемый сценарий.
- Наблюдаемые IP/время/клиент — только авторизованному администратору, без UUID/секретов/ссылок в таблице, с ограниченным хранением и доступом по необходимости. IP не использовать как уникальный идентификатор устройства: учитывать общий NAT, смену сети и общий ключ. Не включать неограниченный access logging ради карточки устройства.
- Приёмка: реальное малое приращение не выглядит нулём; действительно нулевые интервалы не засоряют список; агрегация/часовой пояс/периоды не теряют подтверждённый расход. Проверить общий профиль без individual devices, отдельные доступы, offline/stale/unknown, смену сети и отсутствие метаданных. Реальное отключение по отзыву и точность per-device расхода проверяются отдельно от красивой карточки; mock/heartbeat не заменяют VPN-проверку.

## Параметры каждого подключения: простые defaults и полные настройки

Уточнение пользователя 2026-11-07: основной путь работает с предложенными параметрами без обязательного ручного заполнения технических полей, но все поддержанные настройки выбранного типа подключения доступны в UI при создании и последующем редактировании. Это требования следующей реализации, не утверждение готовности.

- Для VLESS/REALITY TCP, VLESS/REALITY XHTTP, Hysteria2 и WireGuard провести сверку параметров UI/API/runtime с зафиксированными версиями движков и их официальными контрактами. Составить матрицу: параметр, назначение, default/источник предложения, допустимые значения, возможность изменения, влияние на доступ и необходимость перезапуска. Существующие запреты на новые семейства протоколов, AmneziaWG и произвольные expert overrides сохраняются; raw JSON/shell не добавлять. Не выводить неподключённые к backend поля как работающие настройки.
- Для нового подключения предложить адрес, доступный порт нужного transport и допустимые параметры выбранного протокола; генерировать необходимые секреты безопасно. Выбор SNI/target подтверждать проверкой с нужного сервера; при невозможности проверки объяснить причину и дать повтор/ручной ввод без объявления его проверенным. Не считать универсальный preset гарантированно рабочим на любой сети. Сохранённые подключения при открытии редактора не заменять новыми defaults.
- Форма собирается из общих компонентов/композиции и токенов: основной экран с минимальными необходимыми полями и кратким итогом, далее именованные группы «Транспорт», «Защита», «Сетевые параметры» только там, где они применимы. Для каждого сложного поля — короткое объяснение, единицы, ограничения и влияние изменения. Никаких несовместимых сочетаний или огромной плоской формы. Раскрытия, поиск/выбор значений, focus, ошибки, desktop/mobile и reduced motion следуют общим UX-правилам плана.
- Изменения должны проходить полный путь UI → типизированный API → серверная валидация → конфигурация движка → проверка/применение → подтверждение фактического состояния. Перед влияющим на доступ изменением показывать diff и затронутые подключения/пользователей/порты; при ошибке восстанавливать last-good. Не менять ключи/UUID/подписки при обычном редактировании; ротация — отдельное явное действие. Возврат к рекомендуемым параметрам только по запросу с preview, без скрытой ротации секретов/сброса доступа.
- Изменение параметров серверного подключения не расширяет автоматически индивидуальные назначения пользователей. Изменение порта согласовывается с запланированным UFW pipeline, а не остаётся отдельно сохранённым числом. Успех сохранения отделять от подтверждения применения/доступности; показывать понятные applied/pending/failed состояния и следующее действие.
- Приёмка каждого поддерживаемого типа: создание с defaults → реальное клиентское подключение → редактирование применимого расширенного параметра → повторное чтение без потери значений → перезапуск/обновление подписки и повторное подключение → отзыв. Дополнительно целевые проверки несовместимых значений, stale writes, конфликта порта, ошибки apply/rollback и сохранения credentials. Конфигурационные/unit проверки не подменяют внешний handshake; серверные и сетевые gates сохраняются. Проверять короткими блоками без повторения неизменённых PASS.

## Целевой путь

Установка → одноразовый код владельца → собственный логин/пароль → подключение с предложенными параметрами → пользователь → «Подключить» → подписка/QR Happ или Streisand, либо файл WireGuard → реальная проверка расхода и отзыва.

Любой пользователь должен пройти основной путь без первоначальной ручной настройки движков, чтения журналов, выбора TLS-параметров или редактирования JSON. Если автоматизация не удалась, сообщить конкретную причину и следующее действие; подробности открываются отдельно. Значения предлагать по проверкам этого сервера, не объявлять произвольный домен «лучшим».

- Существующие дизайн-токены, Tailwind и Button/Field/Panel/Dialog/Badge; предметные блоки собираются композицией. Общие изменения отступов, ширины и адаптивности вносить в общие компоненты, без копирования CSS/бизнес-правил/API-контрактов по страницам. Не создавать собственный UI-framework или добавлять зависимости без необходимости.
- Один экран «Подключения»: компактная таблица и одна кнопка добавления, один диалог и только одна активная форма протокола. Расширенные настройки доступны по запросу. Состояние службы отдельно от подтверждённого VPN.
- У пользователя понятный диалог подключения: подписка, QR/копирование или отдельный URI; WireGuard — файл. Обязательного выбора приложения нет: выдача доступа не зависит от Happ/Streisand. Инструкции для конкретного клиента — необязательная справка, без лишнего шага основного сценария. Не показывать секретные ссылки раскрытыми по умолчанию.
- Ошибки рядом с действием, ошибки полей рядом с полями, короткие подтверждения. Постоянные предупреждения только при конкретной необходимости. Мониторинг 5s с выбором интервала сохраняется, формы не сбрасываются при обновлениях.
- 2FA — отдельный шаг после проверки логина/пароля, только когда включена. Настройка — в «Безопасности». Вход по одному паролю при включённой 2FA не создаёт сессии.

- Отдельно управлять составом доступа пользователя/подписки: выбирать нужные из созданных и разрешённых подключений, не включать все существующие или вновь созданные автоматически. Для первого пользователя можно предложить только что созданное подключение, с видимым выбором; доступность на сервере и выдача конкретному пользователю — разные состояния. Показывать выбранные протоколы/количество, сохранять выбор при редактировании и обновлении UI. Выбор приложения для этого не нужен.
- Выбранный набор проверяется сервером и одинаково действует для подписки, отдельного URI, QR и устройств; выключенные, отозванные, неподдержанные или не прошедшие publication gates подключения не выдаются. Изменение доступа не пересоздаёт секреты без необходимости. Для уже выданных конфигураций явно различать исключение из подписки и отзыв работающего доступа: обновление списка само по себе не гарантирует отключение клиента. Миграция сохраняет существующие явно выданные доступы без скрытого расширения; после неё новые подключения не добавляются всем пользователям автоматически.
- Для изменений показывать текущие значения и конкретные последствия для клиентов, валидировать на сервере, применять с проверкой состояния и откатом. Без явного действия не пересоздавать ключи/ID/токены и не сбрасывать пользовательские данные. При ошибке сохранять введённые значения, показывать одну понятную ошибку рядом с действием.
- Управление пользователем после добавления: редактирование имени, срока действия/продления, пакета ГБ и остатка, лимита устройств, включения/блокировки/отзыва доступа. Видны расход, срок, устройства, фактическая доступность и причина ограничения; доступны подключение и управление устройствами. Сохранение формы и реальное исполнение лимита — разные проверки. Сохранять существующие запреты на неподдержанные remote/cascade finite quotas; не разблокировать их ради UI.

### Сессии, безопасность и скорость

- Проверить полный сценарий аккаунта: вход, обновление страницы/проверка сессии, истечение и выход, смена логина/пароля с текущим паролем, отзыв прежних сессий и повторный вход. Включённая 2FA сохраняется и остаётся отдельным шагом. Не терять незавершённую форму при обновлении данных; при истёкшей сессии давать понятный безопасный возврат ко входу.
- Панель должна защищать управляемый сервер: серверная авторизация/CSRF, безопасные сессии/cookies и TLS, ограничение попыток/ресурсов, минимальные привилегии и allowlist helper, отсутствие секретов в публичных логах/ошибках, ограниченные журналы, проверяемые обновления/rollback. Сохранить SSH и сторонние службы. Утверждение «максимально защищено» не заменяет проверки конкретных угроз; SSH/network hardening и firewall проходят отдельные предусмотренные gates.
- Надёжность и быстрое подключение — текущий приоритет. Проверить задержки UI/API и реального установления VPN-соединения, ошибки/retry/timeouts и поведение при недоступном движке/сети; исправлять обнаруженные причины. Не обещать универсальную скорость, не отключать TLS/валидацию и не добавлять тяжёлые сервисы ради неё. Достаточные целевые проверки короткими блоками; широкие прогоны только при конкретном риске или выпуске.

### Приватность и длительная работа сервера

- Цель пользователя — снизить отслеживаемость и узнаваемость VPN при сохранении скорости, безопасности и совместимости. Перед изменениями различать угрозы наблюдателя сети/DPI, атакующего на публичную панель и VPS-провайдера; актуализировать существующую модель угроз. Проверять DNS/IPv6 leaks, случайный прямой обход VPN и раскрытие доступа в логах/ошибках/URL. Не обещать невидимость сервера, IP или трафика для всех наблюдателей и не считать выбор SNI доказательством неотслеживаемости.
- Использовать корректные параметры уже согласованных протоколов и проверять поведение настоящего клиента. Административный доступ и пользовательский трафик имеют отдельные границы; наружу выставляются только необходимые службы. Секреты и журналы доступа хранятся минимально необходимое время, с ограничением размера и правами. Не ослаблять TLS/SSH-проверки, MFA или авторизацию ради маскировки/скорости; новые протоколы и непроверенные «stealth» overrides не добавлять.
- Для работы сервера надолго: ограничить рост журналов/SQLite/истории/backup и расход CPU/RAM/диска, проверить освобождение ресурсов и bounded retries; обеспечить понятное состояние при заполнении диска/сетевом сбое, восстановление после reboot, обновление сертификатов, проверяемые обновления и восстановление из резервной копии. Применять ротацию без потери учёта трафика, не удалять пользовательские данные автоматически. Новые SSH/firewall/ACME изменения по-прежнему требуют отдельного rollback gate.
- Подтверждать быстродействие замерами времени подключения, задержки, пропускной способности и нагрузки сервера в указанной сети/клиенте; безопасность — целевыми проверками границ и утечек. Для длительной надёжности выделить отдельный ограниченный по времени сценарий наблюдения и восстановления, не запускать часовые прогоны в обычном UI-блоке. Фактические результаты и оставшиеся ограничения записывать отдельно от требований; гарантий бессрочной работы/отсутствия блокировок не давать.

Пользователь дополнительно запросил удобную установку обновлений из админки. В исходниках уже есть «Безопасность → Обновление ArcVPN», signed upload/apply API и root updater; развивать этот путь, не создавать второй механизм или повторный installer.

- Основной UX: текущая версия → проверить доступное доверенное обновление → увидеть версию, состав/изменения и влияние на подключения → явно запустить обновление. Загрузка подписанного архива остаётся дополнительным способом. Обновления добровольные, без скрытой автоустановки; проверку релизов не связывать с 5-секундным мониторингом.

Принятый запрос не равен успешному обновлению; не показывать бесконечный spinner или потерянный результат после перезапуска. Запретить параллельные применения и сохранить проверки auth/CSRF.

На важной установке предусмотреть согласованный snapshot/backup до применения. Текущие source/unit проверки не выдавать за полную серверную приёмку.

Критерий этого приоритета: пользователь управляет выбранными подключениями и доступом после создания, получает QR/подписку без выбора приложения, проходит сценарии аккаунта, может добровольно установить проверенное обновление через UI и не сталкивается с перекошенными/переполненными формами. Подтверждение — целевой browser/API сценарий на desktop/mobile, security regression для изменённых границ и отдельная реальная серверная проверка затронутого поведения. Это требования, не утверждение о текущей реализации.

## SNI

Встроенный каталог кандидатов — рабочий старт без настройки внешнего источника. Проверки ограничены четырьмя доменами за операцию; каталог шире одной партии. Свой список/файл и внешнее HTTPS-обновление с независимой подписью — дополнительные возможности, не обязательный первый шаг.

Одинаковые активные проверки одной ноды объединяются, новая отличающаяся проверка ждёт завершения текущей. Не смешивать занятость, лимит и недоступный агент в одной ошибке. Недоступный IPv6 не должен отвергать доступный IPv4; сохраняются public-IP/SSRF, сертификат, имя, TLS1.3/h2 и bounded timeouts. Проба SNI не доказывает VPN и не публикует endpoint автоматически.

## Последний блок: сетевые разрешения через админку

Добавлено по прямому решению пользователя 2026-11-07; отложено до конца плана. На стенде Hysteria2 слушает UDP/8444, но в показанном UFW нет разрешающего правила этого порта. Успешный запуск движка не должен скрывать такое несоответствие; блокировка именно UFW и реальный клиентский трафик ещё требуют проверки.

- В админке — компактный раздел сетевого доступа: назначение правила, порт/транспорт, источник (ArcVPN или внешнее правило), фактическое состояние и понятные действия. Обычный путь автоматический; ручное управление доступно в расширенных настройках через существующие компоненты и ограниченный root helper.
- Перед применением показывать конкретный diff. Добавлять только необходимые разрешения, проверять результат; при сбое возвращать предыдущее состояние. Для смены порта сначала подготовить новое разрешение и подтвердить применение подключения, затем убирать ненужное собственное правило. Не удалять правило, ещё нужное другому подключению.
- Сохранять SSH, HTTPS-панель и правила сторонних служб, включая 3x-ui. Удалять только принадлежащие ArcVPN и больше не используемые правила; не присваивать существующие чужие правила. Выключенный firewall автоматически не включать, политики по умолчанию не менять.
- Отдельно показывать ограничения внешнего firewall провайдера: локальное разрешение не доказывает доступность порта из клиентской сети. Не выдавать состояние службы или открытый TCP-порт за подтверждение VPN handshake.
- До реализации — актуализировать модель угроз; изменения и rollback проверить в изолированной VM по правилам проекта. Критерии: нужные TCP/UDP-порты согласованы после создания/смены/удаления и перезагрузки, повтор идемпотентен, общий порт/чужие правила/SSH сохранены, ошибки не оставляют непонятное частичное состояние.

## Базовые протоколы и автоматические порты — уточнение 2026-11-07

- По сообщению пользователя VLESS TCP работает после выбора Firefox. Это не универсальная проверка всех клиентов/сетей. Будущий автоподбор fingerprint должен учитывать результат на клиентской сети; серверная TLS-проба не доказывает совместимость телефона. Рабочие профили не переключать скрыто.
- XHTTP уже создан на 2087; оператор вручную открыл TCP/2087. Его фактический VPN-трафик пока не подтверждён. TCP — нижележащий транспорт, в таблице отдельно обозначать XHTTP и TCP / RAW. Текущая модель допускает один профиль каждого вида; существующие профили редактируются.
- WireGuard: инструменты установлены, forwarding=1, служба inactive/dead, выборка категорий журнала пуста. Причина ошибки не установлена. Нужна стадия ошибки из новой диагностики, затем целевое исправление и реальное подключение.
- Автоматический firewall перенесён в ближайший обязательный функциональный блок: открыть новый необходимый порт, применить и подтвердить службу, удалить только собственное неиспользуемое старое правило; при ошибке откатить изменения. Сохранять SSH, панель, ACME, общие порты и чужие правила 3x-ui. Статус процесса не означает доступность VPN. Управление и план изменений доступны в админке.
- Реализация сетевых изменений остаётся за gate AGENTS.md: актуальная модель угроз и rollback-тесты в изолированной VM. Текущий VPS с сохраняемой 3x-ui не является изолированным стендом. Автоматизация UFW ещё не выполнена; ручные правила не считать управляемыми без явного принятия.
- Каскады отложены до исправления базовых протоколов, управления пользователями, настроек и firewall.
