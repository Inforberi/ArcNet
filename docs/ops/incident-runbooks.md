# Операционные сценарии: безопасное восстановление

Документ описывает требуемое поведение будущей системы. Команды и реальные процедуры появятся после реализации и тестов.

## 1. Новый сервер недоступен сразу после изменения firewall

1. Операция остаётся `verifying`, не `success`.
2. Rollback timer на сервере возвращает последние managed rules (не трогая чужие).
3. Панель проверяет восстановление SSH/Agent с другого подключения.
4. В интерфейсе: какой порт был недоступен, что откатилось и что осталось ручной задачей.
5. Если возврат невозможен из-за provider firewall/потери сервера — показать ссылку на провайдерскую rescue-консоль, не обещать восстановление.

## 2. Сервер выходит из строя или IP блокируется

1. Статусы Xray/endpoint/health отличаются от факта последнего heartbeat.
2. Если жив другой выход — переключить новые соединения в рамках явной fail-policy.
3. Если умер входной VPS — заранее разосланные запасные клиентские endpoint и независимый сервис подписок; гарантии автоматического выбора клиента нет.
4. `Заменить VPS`: сохранить logical endpoint и пользователей, безопасно bootstrap нового VPS, выполнить external probe, затем publish subscription revision.
5. Не считать IP-URL долговечным при гибели сервиса подписки; нужен известный заранее резервный адрес.

## 3. Потеря панели управления

- Удалённые агенты используют last-good Xray config и не прекращают VPN автоматически.
- Восстановить SQLite и master key из зашифрованной независимой резервной копии; сверить доверенные node identities и конфигурационные ревизии.
- Ноды могут обслуживать трафик без панели, но новые централизованные ограничения и изменения не применяются до восстановления управления. Политика квот должна явно описывать stale state.

## 4. Ошибка обновления Xray/агента

- Staged version rollout → локальный service/config test → end-to-end probe → commit.
- При отказе — возврат last-good бинарника/config (если версия допускает обратимость), `degraded/failed` и журнал для диагностики.
- Нельзя обновлять все ноды одновременно по умолчанию; обязательна практика тестового обновления одной ноды.

## 5. TLS-IP renewal не прошёл

- Уведомление заранее; повторные попытки с backoff без ACME rate-limit abuse.
- Диагностика: доступность выбранного ACME challenge, ip identifier, часы, сертификат, reload.
- Продолжать обслуживать текущий сертификат до expiry; не выключать проверку TLS.
- При истечении объяснить, что HTTPS-сервис недоступен для доверенной проверки, и предложить восстановление через доверенный административный канал.
