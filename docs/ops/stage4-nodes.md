# Текущие замечания к нодам ArcVPN 0.6.5-stage4

SSH bootstrap поддерживает публичные IPv6 literals и SCP bracket syntax; приватные, link-local, documentation IPv4/IPv6 по-прежнему блокируются. У агента при потере контроллера bounded backoff с jitter до 5 минут; VPN продолжает работать независимо от контроллера. Terminal control-plane journals ограничены TTL/размером, активный install marker не удаляется. AES node-control key защищён no-follow и file mode 0600. **Это изменения исходников, на VPS не испытаны.** См. [отчёт](../release-0.6.5-stage4-source-audit.md) и [внешние сценарии](../testing/stage4-codex-handoff.md). Исторические разделы ниже не заменяют текущий статус.

# ArcVPN — удалённые ноды, сборка и безопасная проверка (0.6.3 source preview)

**Состояние:** исходники этапа 4 содержат SSH-установщик и управление VLESS Reality TCP, но ни один VPS и внешний VPN-клиент в данном окружении не проверялся. Это не инструкция для production. Экспериментировать только на отдельном VPS с snapshot, консолью провайдера и резервным SSH-доступом. [Протокол внешней проверки](../testing/stage4-codex-handoff.md).

## Поддерживаемый профиль

- Контроллер: публичный HTTPS origin ArcVPN, реальный сертификат, администратор с MFA. Работа по публичному HTTP заблокирована.
- Нода: чистая Debian/Ubuntu Linux `amd64`, `systemd`, `apt-get`, Ed25519 SSH host key, root или passwordless sudo, доступ на SSH по ключу.
- Только **один** управляемый inbound VLESS TCP + Reality на ноде; остальные профили из этапа 2 не распространяются на удалённые ноды автоматически. Одновременные установки ограничены двумя.
- Агент инициирует соединение к контроллеру по HTTPS, предъявляет индивидуальный bearer credential. Сервер подтверждается обычным TLS PKI, **mTLS не реализован**. Секрет можно отозвать; ротация двухфазная.
- Действующая конфигурация Xray сохраняется при отключении контроллера. Реальная доступность VPN проверяется внешним клиентом, heartbeat и systemd не заменяют handshake.

## Сборка и доверенная поставка

1. На доверенной Linux amd64 release-машине получить настоящий production бинарник ArcVPN и совместимый Linux amd64 Xray. Для полного релиза потребуется сетевой `npm ci` с реальным `frontend/package-lock.json` и `scripts/build-release.sh` — в переданном source-архиве lockfile отсутствует. На dev-машине можно собрать Go отдельно, но это **не готовый релиз**.
2. Отдельную пару Ed25519 создавать и хранить **вне контроллера и ноды**: `arcvpn update-keygen --out-dir ...` (`docs/ops/signed-upgrades.md`). Приватный ключ не копировать на VPS.
3. На доверенной машине выполнить `scripts/build-stage4-node-bundle.sh` с пятью обязательными аргументами: исполняемый ArcVPN `amd64`, подписываемый Xray `amd64`, путь к приватному ключу, неизменная версия, новый ZIP. Скрипт вызывает `arcvpn update-sign --xray ...`. Он не скачивает компоненты из сети.
4. Установить на контроллер **только** полученный подписанный ZIP и соответствующий публичный Ed25519-ключ по независимому каналу. Пример расположения: `/etc/arcvpn/node-release.zip` и `/etc/arcvpn/node-release-public.hex`. Их должен читать пользователь службы `arcvpn`, но запись разрешается только root. Указать системной службе `arcvpn-panel.service` параметры `Environment=ARCVPN_NODE_RELEASE_BUNDLE=/etc/arcvpn/node-release.zip` и `Environment=ARCVPN_NODE_RELEASE_KEY=/etc/arcvpn/node-release-public.hex`, затем `systemctl daemon-reload && systemctl restart arcvpn-panel.service`.
5. Проверить, что панель открыта по `https://...`, имеет правильный `--public-url` (его передаёт стандартный `install.sh`) и аутентифицированный администратор видит страницу «Серверы».

**Никогда не отключать проверку подписи.** Подпись защищает только целостность/происхождение выбранных бинарников относительно закреплённого ключа. Она не доказывает их безопасность, совместимость или работу сети.

## Установка из интерфейса

1. В «Серверы» указать DNS/IP, SSH-порт, SSH-пользователя и свободный VPN-порт. Публичный IP обязателен; частные, loopback, link-local, cloud metadata, тестовые диапазоны блокируются.
2. Получить SSH Ed25519 fingerprint; **сверить через независимую консоль провайдера** с `ssh-keygen -l -f /etc/ssh/ssh_host_ed25519_key.pub`. Один лишь `ssh-keyscan` не доказывает подлинность.
3. Вставить временный SSH private key в форму, выполнить read-only preflight, проверить конфликты, требования и план изменений. Ключ не сохраняется в SQLite, передаётся в ограниченный Go worker через HTTPS и временный файл 0600, удаляемый после операции. Возможные следы памяти процесса и аварийных дампов требуют отдельного внешнего аудита.
4. Подтвердить установку. Операция хранит ID и статус в SQLite; закрытие вкладки её не отменяет. Если контроллер перезапустится, операция будет помечена как прерванная, а не успешная. Если установка частично завершилась, **не повторять автоматически** без проверки VPS через provider console.
5. SSH-bootstrap ставит проверенные бинарники, изолированные systemd-службы, `arcvpn-node` и `arcvpn-xray`, затем регистрирует агент через одноразовый token **по stdin**. В persistent Xray root-helper доступен только типизированный `apply_xray_v1` через Unix socket с SO_PEERCRED.
6. После подтверждения `desired_revision == applied_revision`, статуса Xray `active` создать тестовую VLESS-ссылку из админки и проверить handshake + egress **на отдельном клиенте**. Пока нет внешнего probe, `vpn_probe=unknown`, `published=false`; удалённые ноды **не публикуются в подписки**.

## Ограничения и восстановление

- SSH-установщик **не меняет** sshd, UFW и облачный firewall. Поэтому TCP VPN-порт необходимо открыть вручную только после оценки сетевой политики, сохраняя SSH. Отсутствие изменения firewall не означает доступности порта снаружи.
- Ограниченный rollback при ошибке install-script удаляет только созданные этим запуском файлы/units и системных пользователей. Нельзя гарантировать откат установленных `apt`-пакетов или внешнего firewall; обрывы питания и SSH требуют console recovery.
- `arcvpn-node-xray.service` работает от непривилегированного `arcvpn-xray` с `CAP_NET_BIND_SERVICE` для 443. Конфиг `/etc/arcvpn-node/xray.json` принадлежит root / группе `arcvpn-xray` (0640). Агент не может его менять напрямую. Receipt `/var/lib/arcvpn-node-root/last-apply.json` root-only: агент не может подменять историю last-good.
- При отказе `xray run -test` новая конфигурация не устанавливается. При ошибке restart применяется прежний файл и выполняется повторный restart прежней службы (если возможен). Повтор контроллера использует тот же operation ID. Свыше восьми доставок без ACK операция становится `failed` и требует ручного Retry.
- Отзыв в панели прекращает управление нодой, но **не останавливает её Xray**. Managed-only uninstall и подписанный SSH upgrade реализованы на уровне исходников и требуют SSH confirmation; локальный rebind выполняется CLI. **Ни один из них не испытан на VM**. В версии 0.6.1 внешнего probe ещё не было (в 0.6.3 добавлен отдельный CLI, см. раздел ниже): до вывода VPS из эксплуатации использовать независимую provider console и аудит созданных ресурсов. Не удалять `/opt/arcvpn-node` вручную без безопасной остановки служб.
- Старый HTTP `/node-install.sh` намеренно отключён; незаверенную `curl | sh` команду не использовать. Альтернативный `arcvpn node-install` **написан в коде** и требует заранее проверенного локального бинарника ArcVPN, подписанного ZIP и публичного Ed25519 ключа. Повторная установка на уже managed VPS **отклоняется**. Реальное выполнение на чистой VM ещё не проверено — `S4-34` полностью не закрыт.
- React `npm ci/typecheck/build` в текущем окружении заблокирован DNS npm registry, ни одного фиктивного lockfile в проекте нет. Проверки перенести на сетевой CI.

**Границы приёмки:** [что сделано в коде](../release-0.6.1-stage4-continuation.md), [чеклист](../planning/stage4-checklist.md), [внешние испытания](../testing/stage4-codex-handoff.md).


## Дополнение 0.6.1: локальная установка и обслуживание managed VPS

**Общее условие:** ниже команды для отдельной тестовой Linux amd64 VM. Перед запуском — snapshot, независимая провайдерская консоль и проверка подписи/host key. В работе с production не применять до внешней приёмки `docs/testing/stage4-codex-handoff.md`.

### Одноразовая локальная установка

Пример после независимой передачи доверенного **исполняемого** `/root/arcvpn`, проверенного `/root/node-release.zip`, `/root/node-release-public.hex` и выдачи одноразового токена на контроллере:

```bash
sudo /root/arcvpn node-install \
  --signed-bundle /root/node-release.zip \
  --public-key /root/node-release-public.hex \
  --controller https://vpn.example \
  --vpn-port 443 \
  --token-stdin
```

Токен ввести отдельной строкой после запуска (stdin), не передавать через `--token`, переменные окружения или argv. Программа делает local preflight, подписанный install, пытается зарегистрировать ноду и запускает агента. Возвращённый installation ID — важное доказательство происхождения managed-файлов. **После успешной регистрации нужно отдельно развернуть Xray-конфигурацию из контроллера, получить ACK и проверить VPN с внешнего клиента.** Если возвращена ошибка, проверить `node.json`, root-owned marker и systemd через консоль до повторной попытки.

### Удаление через UI и локально

UI: «Серверы» → «Удалить с VPS» → выбрать `detach` (сохранить Xray, отозвать управление) или `purge` (остановить Xray, удалить только ArcVPN-managed компоненты), сверить Ed25519 fingerprint, SSH private key → plan → отдельно подтвердить ID оригинальной установки. После получения успешной SSH квитанции контроллер отзывает identity. **Режим revoke-only не останавливает Xray.**

Локально после snapshot и сверки `sudo cat /etc/arcvpn-node/.arcvpn-managed`:

```bash
sudo /root/arcvpn node-remove --mode detach --confirm REMOVE_MANAGED_ARCVPN
```

или

```bash
sudo /root/arcvpn node-remove --mode purge --confirm REMOVE_MANAGED_ARCVPN
```

Отдельно отозвать старую node identity на панели. Операции не используют произвольный пользовательский путь для удаления. `purge` завершится ошибкой, если в управляемой директории неожиданно остались чужие файлы (консервативный `rmdir`, без рекурсивного удаления).

### Перепривязка к новому контроллеру

Сначала отозвать identity на **старом** контроллере, затем выпустить одноразовый enrollment token на новом; проследить, чтобы новый контроллер действительно смог достигнуть этого VPS, а Xray с прежней рабочей конфигурацией оставался активным. На самой ноде:

```bash
sudo /root/arcvpn node-rebind \
  --controller https://new-vpn.example \
  --token-stdin \
  --old-controller-revoked
```

Нодовый CLI останавливает только агент на время атомарной замены identity и запускает его обратно, Xray не затрагивает. Если регистрация на новом контроллере не принята, прежний `node.json` сохраняется. **Процедура не переносит автоматически желаемую ревизию и не меняет опубликованные VPN endpoint**; их нужно проверить отдельно.

### Подписанное обновление 0.6.0 → 0.6.1 через панель

1. На контроллер положить подписанный **более новый** release ZIP с агентом и Xray, чей фактический `arcvpn version` совпадает с manifest `0.6.1-stage4`. Публичный Ed25519 verification key закреплён вне панели. Не подменять его ключом из текущего ответа сервера.
2. В «Серверы» → «Обновить Xray/агент»: проверить root-owned managed marker и IP, SSH Ed25519 fingerprint через независимую консоль, текущую версию и целевую версию; утвердить план.
3. Контроллер проверяет подпись и отдаёт команду только фиксированному SSH install origin. Remote update копирует новый agent/Xray в защищённый stage, валидирует candidate Xray с текущим конфигом, сохраняет предыдущие бинарники, меняет только свои systemd units и после local active-check пишет новую версию. При ошибке выполняется попытка rollback бинарников и units.
4. `status=upgraded` означает только **локальный receipt**, не подтверждённый handshake. Проверить подлинную работу с отдельного VPN-клиента, текущую ревизию, IP/состояние и аварийный откат. Запрет на downgrade (`0.6.1` → `0.6.0`) и смену 0.6.x на другой major/minor — fail-closed.

### Невыполненные проверки и ограничения

- Настоящее `npm ci/typecheck/build`, browser E2E и VPS/SSH/systemd/Xray/VPN всё ещё **NOT RUN**. Не использовать `sh -n` как доказательство работы shell на Debian/Ubuntu.
- `node-install` не скачивает доверенный verifier или подписанные артефакты автоматически: оператор отвечает за проверенное размещение файлов. Это защищает от незаверенного `curl | sh`, но усложняет установку по сравнению с полностью self-contained bootstrap.
- Нельзя гарантировать восстановление после SIGKILL, потери SSH/питания в момент бинарной замены. Проверить файлы и услуги через provider console. Объединённый `go test -race` всего HTTP API не завершился в текущем окружении, поэтому marked **TIMEOUT**, а не PASS.
- Нынешний протокол управления — TLS server auth + индивидуальный bearer-secret, **mTLS нет**. `agent_protocol=1` — проверка совместимости команд, а не криптографическая подпись каждой команды по отдельности.

## Дополнение 0.6.2 — проверки сети, подписи и вывод ноды из выдачи

- SSH preflight для ноды с публичным HTTPS-контроллером делает read-only запрос `GET <controller-origin>/healthz` с VPS. Ожидает HTTP **204**, требует обычную проверку TLS CA, не следует редиректам и не посылает enrollment token. `unreachable` / `unexpected_status` блокируют удалённую установку; `unverified_no_curl` оставляет явное **предупреждение**, не успешную проверку. Предупреждения UFW/nft/cloud firewall не меняют SSH или VPN порт.
- Signed install и upgrade сверяют SHA-256 **после** копирования в root-owned конечный/временный путь, не доверяя user-owned `/tmp` как долгоживущему контейнеру проверенных байтов. При невалидном candidate Xray, прежний сервис не перезапускается. При ошибке после начала замены делается попытка rollback; нарушение питания требует проверки файлов и служб в rescue console.
- После потери SSH-ответа контроллер проводит read-only сверку managed marker, подписанных хешей, версии, systemd и состояния detach/purge; только однозначное полностью установленное состояние допускается как успех. Пустой SSH-ответ сам по себе успехом не является.
- **Новая операция drain:** на странице «Серверы» выбрать **«Drain: скрыть ссылки»**. Для API — `POST /api/nodes/{id}/drain` с JSON `{"draining":true}`. Новые диагностические VLESS-ссылки временно недоступны (HTTP 409), `published=false`, но **все ранее сохранённые клиентские ссылки и уже установленные VPN-сессии могут продолжать работать**. Это не аварийная остановка, не отзыв пользователей и не проверенный сетевой drain. **«Возобновить выдачу»** допускается только при подтверждённой последней ревизии и не публикует ноду в подписках. Действительную деактивацию VPN выполнять через `detach`/`purge` с отдельной проверкой.
- Скрипт `tests/react_e2e.py` скорректирован под текущую страницу Nodes; тестировать только после создания настоящего lockfile и production React-сборки. Внешние сценарии [здесь](../testing/stage4-codex-handoff.md).


## Дополнение 0.6.3 — внешний клиентский Xray/Reality probe

1. Подготовить **отдельную тестовую Linux-машину в независимой сети**. Установить доверенный и проверенный исполняемый Xray, получить CLI ArcVPN `0.6.3-stage4` по доверенному каналу. Ни production Xray, ни его версия с сервером не проверялись в исходном окружении.
2. Дождаться `desired_revision == applied_revision` и `deployment_status=applied` в панели. В разделе «Серверы» открыть тестовые VLESS-ссылки, выбрать действующую. Сохранить **всю ссылку** без преобразований в локальный файл `vless.txt` с правами 0600 (не передавать через argv). На панели создать одноразовый grant (TTL 5 минут) и безопасно передать token внешнему оператору; не сохранять в shell history, логи, публичные каналы.
3. CLI `arcvpn node-probe --link-file ./vless.txt --xray /usr/local/bin/xray --controller <HTTPS origin> --node-id <выданный ID> --revision <ревизия> --digest <SHA-256> --report-token-stdin`. **Вместо угловых скобок** подставить фактические значения из панели — в исходниках нет секретов или рабочих адресов. Токен передать строкой на stdin. Для offline probe достаточно `arcvpn node-probe --link-file ./vless.txt --xray /usr/local/bin/xray` без `--controller` и токена; тогда он **не изменяет** серверный статус.
4. CLI запускает `xray run -test` и отдельный Xray-процесс с единственным `vless` outbound и localhost SOCKS5. Пробует HTTPS `https://www.gstatic.com/generate_204`, ожидает HTTP 204. Нет прямого обхода VPN, по ошибке `pass` не возвращается. В отчёте CLI отсутствуют UUID, VLESS secret, public key и grant token.
5. При совпадении grant/revision/digest сервер отмечает `pass` либо `fail` и timestamp; спустя 30 минут он отдаёт `stale`; новая ревизия/удаление/upgrade/drain сбрасывают результат. `pass` **НЕ публикует ноду автоматически** и не подтверждает трафик всех пользователей/протоколов.

**Trust boundary:** любой обладатель неиспользованного grant может отправить `pass` без фактического запуска Xray. Это **не** remote attestation. Назначать grant только доверенному оператору, запускать на контролируемой независимой машине, сохранять очищенные exit codes и доказательства из другой сети в `docs/testing/external-results/`. Без этого реальный VPN остаётся `EXTERNAL_PENDING`. Ошибка `npm` блокирует настоящий React build; CLI/HTTP grant можно тестировать Go unit средствами без React.
