# Аудит исходников ArcVPN перед этапом 4

**Дата проверки:** 2026-11-04. **Исходный артефакт:** `arcvpn-stage3-0.5.1-complete-source-handoff.zip` (181 запись ZIP). **Версия, которую сообщает исполняемый файл:** `0.5.1-stage3-code-handoff`.

## 1. Вывод и область доказательств

**Подтверждённое состояние:** архив содержит реализацию **кодовой части этапа 3 для передачи на проверку**. По дорожной карте следующий этап разработки — **4: добавление и обслуживание нод**. Его основной функционал ещё не реализован. Нельзя считать этапы 1–3 `ACCEPTED`, пока нет протоколов внешней проверки. Статус 4: `PLANNED / NOT STARTED` (есть прототип телеметрии из более раннего этапа).

Проверка основана на предоставленных исходниках и локальных командах. Не получены: доступ к реальным VPS, измерения VPN-трафика, evidence от Codex, доступ к npm-зависимостям для полного frontend build. Содержимое предыдущей переписки напрямую не проверялось; слова из документации сверены с файлами в архиве, но не с внешним стендом.

## 4. Выявленные несоответствия и риски

### P0 — перед установкой ноды / публикацией VPN

1. **Утечка одноразового секрета через аргументы команды.** `frontend/src/pages/Nodes.tsx` строит `curl ... | sudo bash ... --token '<token>'`; `web/node-install.sh` передаёт тот же токен в `curl -H ...` и в `node-register --token ...`. Секрет может оказаться в shell history/списке процессов и диагностике. Это противоречит `docs/features/nodes-and-installer.md`, пункт «не помещать секреты в командную строку процесса». **Не рекомендовать текущую команду для production.** Требуется bootstrap без секретов в argv и с явно ограниченным временем жизни; результаты тестировать на живом Linux.
2. **Bootstrap не проверяет отдельную подпись релизного бинарника.** Скрипт проверяет SHA-256 бинарника, но получает и бинарник, и хеш с одного controller endpoint (`/node/binary`). Это обеспечивает обнаружение несогласованной загрузки по защищённому HTTPS, **не независимое подтверждение происхождения**. Этап 4 должен определить и реализовать pinned release/signature trust и безопасное обновление нод. Текущий код не заявляет такую гарантию.
3. **Нет remote apply/reconcile/last-good.** `internal/nodeagent/agent.go` посылает heartbeat и Xray status; ни установка VPN-движка, ни передача конфигурации, ни atomically acknowledged applied revision не реализованы. Статус online не значит VPN-healthy.
4. **Нельзя подтвердить приёмку 1–3.** В архиве отсутствуют результаты live VPN, реального HTTPS сертификата, backup restore, UFW/systemd/upgrade и React production E2E. Не использовать архив как проверенный production-релиз.

### P1 — блокеры воспроизводимости и развития

5. `frontend/package-lock.json` отсутствует: `scripts/build-release.sh` по контракту завершится до сборки React. Lockfile требуется создать и закоммитить на машине с доступом к registry, проверить `npm ci` на чистой среде.
6. `internal/nodeagent/agent.go` сообщает `Version = "0.3.0-preview"`, в то время как весь handoff имеет версию 0.5.1. Это предварительный идентификатор агента, не текущая версия релиза; унифицировать versioning в рамках этапа 4.
7. `internal/store/portable_nodes.go` и backup v3 сохраняют хеши секретов нод, но **не** обновляют URL старого контроллера в конфиге установленного агента. После смены адреса нужна отдельная процедура rebinding/rotation, иначе heartbeat может исчезнуть.
8. `docs/ai/index.md` ранее вёл сначала на stage1 checklist и `AGENTS.md` содержал устаревший абзац про 0.3.3. В этом документальном handoff актуальные указатели заменены, историю оставили только как историю.
9. Прототип `web/node-install.sh` устанавливает unit мониторинга; запуск на VPS меняет пакеты, пользователя и systemd, но не проверяет конфликт с существующими сервисами как полноценный SSH/preflight wizard. Требуются journal/rollback/idempotence тесты.
10. **Непокрытая часть исходного scope этапа 3:** `docs/planning/roadmap.md` обещает безопасное управление TLS/SSH/firewall, а `docs/features/server-security.md` — раздел SSH и план/rollback hardening. В текущем `frontend/src/pages/Security.tsx` есть UFW/logs/updates, но нет управления SSH; в Go API не найдено endpoints безопасного изменения sshd. Текущий UFW API, наоборот, явно запрещает SSH mutation. Следовательно, **«этап 3 полностью реализован в коде» не доказано относительно исходной дорожной карты**. До внешнего `ACCEPTED` отдельно завершить SSH hardening по требованию или письменно согласовать перенос этой части в этап 4; нельзя незаметно считать её закрытой.

## 5. Учёт статусов этапов (без приписывания внешних результатов)

| Этап | Кодовые исходники | Фактический gate на 2026-11-04 | Следующее действие |
|---|---|---|---|
| 1 — основа и React | Предварительная реализация | `EXTERNAL_PENDING`; React production build не подтверждён | lockfile, CI сборка, UI E2E, чистая VM |
| 2 — VPN-протоколы | Предварительная реализация | `EXTERNAL_PENDING`; handshake не подтверждён | реальный тест каждого профиля, AWG сборка |
| 3 — безопасность VPS | `0.5.1` code handoff, Go PASS; SSH hardening из roadmap не найден | `EXTERNAL_PENDING`, **scope gap** + нет VPS доказательств | закончить/согласовать SSH scope; `docs/testing/stage3-codex-handoff.md` |
| **4 — удалённые ноды** | Только ранний telemetry/enrollment preview | **`PLANNED / NOT STARTED`** | `docs/planning/stage4-checklist.md` |
| 5–7 | Requirements / roadmap | `PLANNED` | После готовности соответствующих зависимостей |

**Оговорка:** разрешено разрабатывать этап 4 параллельно с внешней проверкой этапов 1–3, как предусмотрено дорожной картой. Но этап 4 нельзя принимать, пока не работают все его обязательные end-to-end сценарии на втором VPS. Обнаруженные stage1–3 ошибки должны исправляться приоритетно, если блокируют stage4.
