# Отказоустойчивость: граница сервера и VPN-клиента

## Проверяемые факты и ограничения

- Heartbeat от Go Agent показывает доступность управления и системы, но ничего не доказывает о доступности VPN с конкретного клиента.
- Локальная проверка TCP/UDP сервиса на VPS показывает его состояние на сервере; не выявляет блокировку провайдером пользователя.
- По одному серверному ping невозможно выбрать лучший протокол для всех клиентов. RTT клиента до входного VPS и RTT выхода в интернет — разные величины.
- При отказе выходного VPS входной Xray может направить новые подключения через резервный выход. Активные TCP-сессии могут оборваться.
- При отказе входного VPS переключение зависит от возможностей клиентского приложения и заранее известных альтернативных входов. Изменение серверной подписки не переподключает уже работающий туннель автоматически без участия клиента.
- Отсутствие домена упрощает зависимость от DNS, но IP сервера виден сети и может быть заблокирован. Полная скрытность/необнаружимость не гарантируются.

## Рекомендуемая модель данных (проектируется, НЕ реализована)

- `LogicalEndpoint`: логическая точка подключения пользователя, независимая от VPS.
- `Node`: физический VPS, статус control plane, состояния VPN-процессов.
- `ProtocolHealth`: отдельные результаты по TCP/UDP-протоколам, проверенные независимыми наблюдателями.
- `RoutePolicy`: entry node, список выходов, приоритеты, timeouts, fail-closed/fail-open.
- `ClientCapabilities`: список поддерживаемых протоколов, механизмы обновления профиля и переключения.
- `SubscriptionRevision`: опубликованная и сохранённая конфигурация, резервные адреса подписок.

## Рекомендуемый алгоритм (НЕ реализован)

1. Пассивные сигналы: системное состояние, Xray process health, ошибки и таймауты в пределах допустимых данных.
2. Активные независимые проверки: TCP handshake, реальный TLS/VLESS или UDP/QUIC handshake из внешних точек, контроль выхода в интернет.
3. Решение о деградации только после нескольких подряд провалов (например, параметризуемый порог), избегая jitter/false positive.
4. Cooldown и hysteresis для предотвращения постоянного переключения маршрутов.
5. Обновление выходного balancer без изменения клиентского профиля, с выбором резервного выхода и fail-closed по умолчанию.
6. При отказе входа — обновить постоянную подписку и резервные адреса; не заявлять «автофейловер» для клиента без подтверждения соответствующей функции Happ.
7. Протоколы не сравнивать глобально только по ping; при наличии телеметрии клиента отделять RTT, потери и фактическое прохождение данных и применять переключение на стороне клиента.

## Приёмка

- Измерение одновременно: нода online, VLESS reachable, Hysteria2 unreachable с клиентского стенда.
- Искусственно блокировать входной IP в клиентской сети: серверный ping остаётся успешным, клиентский тест падает.
- Отказ NL выхода: новые запросы идут DE, запрещён обход напрямую при fail-closed.
- Кратковременная потеря пакетов не вызывает многократного переключения.
- Отдельно протестировать Happ на каждой поддерживаемой ОС с текущей версией и настроенной подпиской.
