# Инварианты надёжности и безопасности

## Угрозы

1. Компрометация центральной панели даёт возможность управлять всеми нодами — изолировать доступ, использовать TOTP, audit и scoped credentials.
2. Подмена SSH-хоста при установке — обязательная проверка host key с понятным подтверждением изменения.
3. Подмена бинарников Xray/агента — проверять подписи/хеши, фиксировать версию, выполнять rollback.
4. Ошибка UFW/SSH — потеря доступа ко всем VPS — нужен проверенный fallback/rollback timer.
5. Утечка subscription URL или QR — доступ к VPN; считать секретом.
6. Сбой/сетевая перегородка при раздаче quotas — задержка общего учёта; точно определить max stale/offline.
7. Ошибочная отправка трафика напрямую при отказе каскада — fail-closed default.
8. Перегруженные heartbeat/metrics workers — bounded scheduler, backoff и ресурсные лимиты.
9. Выдача ошибок с секретами — redact sensitive fields в логах, HTTP и UI.
10. Cross-site request forgery / stolen browser session — CSRF/Origin + cookie hardening + authorization на каждый защищённый API.

## Безопасность системных действий

- Privileged helper владеет ограниченными операциями: `AllowPort`, `RevokeManagedPort`, `RestartManagedService`, `InstallVerifiedBinary`, `ApplyApprovedFirewallPlan` (названия условные контракты, не API).
- На ноде запрещён произвольный `exec` от управляющей панели. Аргументы строго структурированы, проверяются, пути ограничены.
- Проверять, что порт действительно слушается и доступен извне; UFW не контролирует firewall провайдера.
- Не изменять пользовательские правила UFW «по своему разумению». Порт закрывать только когда нет зависимостей и правило принадлежит панели.
- Для Podman/Docker отдельно проверять netfilter, host networking и видимость исходных IP; контейнеры не являются обязательной архитектурой.

## Reconciliation / Rollout

`planned → validated → staged → applying → verifying → active`, а при сбое `rollback_pending → rolled_back/failed`. Уникальный operation ID и revision. Для нескольких VPS нет атомарной общей транзакции: применять последовательно, использовать компенсации и показывать частичный статус.

## Health и failover

- `agent_online` не равно `xray_running`, не равно `inbound_reachable`, не равно `route_working`.
- Переход на резерв после нескольких провалов и внешнего подтверждения, с hysteresis/cooldown; не переключаться каждую секунду.
- При отказе egress новые сессии через резерв; старые TCP могут оборваться.
- Если входной VPS заблокирован, выбор другого требует заранее доступного профиля у клиента; панель в недоступном VPS ничего не исправит.
- Нельзя автоматически менять подписку без альтернативного доступного канала и возможностей клиентского приложения.

## TLS и отсутствие домена

- HTTPS панели и подписок допускает публичный IP с сертификатом, удостоверяющим IP SAN. Проверка TLS всегда включена.
- Для краткосрочных IP-сертификатов автоматическое обновление и предупреждение о сбое критичны.
- Reality — отдельная сущность, не использующая этот TLS-сертификат панели по умолчанию.
- Сервис подписок должен быть логически независим от входных VPN-серверов; на одном VPS полной независимости физически нет.

## Резервные копии

Шифрованный SQLite snapshot + необходимые для восстановления secrets/keyring/metadata. Для remote backup — отдельное хранилище. Регулярная тестовая процедура восстановления, а не только факт создания файла.
