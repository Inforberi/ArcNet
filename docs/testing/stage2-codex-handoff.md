# Codex: внешняя приёмка этапа 2

**Статус:** кодовый кандидат 0.4.3, внешняя приёмка **НЕ ПРОЙДЕНА** (её ещё не запускали).

## 0. Изоляция

Использовать чистый тестовый VPS и тестовые устройства, без рабочего 3x-ui и без реальных клиентов. Не публиковать IP, файлы `.conf`, API-куки, ключи и пароли в логах задач. Снять снапшот VPS. Перед тестом проверить действующий SSH и управление через out-of-band console.

## 1. Сборка frontend и backend

В машине с интернетом и Linux x86_64:

```bash
cd frontend
npm install --package-lock-only --ignore-scripts
npm ci
npm run build
cd ..
go test ./...
go vet ./...
go test -race ./internal/app ./internal/httpapi ./internal/backup ./internal/protocols ./internal/engines
./scripts/build-amneziawg.sh # отдельная проверка upstream (Go >=1.25)
./scripts/build-release.sh
./dist/arcvpn-linux-amd64 frontend-check
```

`package-lock.json` добавить в репозиторий. Если React не собирается, устранить ошибки TypeScript и реального npm build, **не** подменять фронтенд статическим макетом. Запустить `tests/react_e2e.py` в доступном браузерном окружении на 320, 390, 768, 1024, 1440 px, включая новый экран протоколов и QR.

## 2. Системная установка

После резервирования тестового VPS и проверки SSH, выполнить `sudo bash install.sh`. Проверить HTTPS-сертификат по IP через обычную валидацию CA (`curl --fail https://IP:8443/healthz`, без `-k`), renew, systemd, permissions. При сбое инсталлятора собрать журнал и откатить VPS к снапшоту. Установщик не использует рабочий 3x-ui.

## 3. Протоколы

Для каждого профиля по отдельности:

1. Создать профиль из React UI; убедиться, что API вернул применённую конфигурацию, а systemd-сервис `active`. Если движок не установлен, UI должен показывать ошибку, не утверждать успешное включение.
2. На **другом устройстве и из другой сети** проверить подключение и выходной IP. Не ограничиваться `ping`, `ss` или `systemctl is-active`.
3. VLESS TCP Reality: проверить QR и URL. XHTTP: проверить с реальной версией Xray и клиентом, поддерживающим XHTTP. Hysteria2: проверить UDP/QUIC, правильный SNI/IP TLS, не использовать `insecure: true`.
4. WireGuard: подключение из WireGuard-клиента, handshake `wg show arcwg`, DNS, IPv4 интернет и ограничения NAT. Проверить UDP-порт на облачном firewall.
5. AmneziaWG 3.1: **не ставить вручную старый модуль**. Сначала проверить, что `scripts/build-amneziawg.sh` собирает pinned upstream tags `v3.1.20260812` и `v3.1.20260828` под Go >=1.25, что `dist/SHA256SUMS` содержит три binaries и два архива соответствующих исходников. На VPS проверить `amneziawg-go --version`, вывод `awg`, команду `awg-quick strip` для сгенерированного профиля и запуск именно userspace через root CLI. Проверить реальный AWG 3.1 handshake и IPv4 egress из внешней сети. Не принимать обычный WG за AmneziaWG.
6. Создать двух пользователей, отключить одного; проверить, что отключение вступило в силу для **каждого** движка. Удалить второго, проверить отзыв ключей/паролей.
7. Включить/отключить каждый профиль, проверить смену port/health, ошибки при занятом порту, rollback при неудачном restart.

## 4. Перенос и безопасность

1. Сохранить backup ArcVPN v2 с активными VLESS/XHTTP/Hysteria2/WG/AWG. Загрузить на отдельный VPS и восстановить; сверить UUID, ключи, адреса клиентов и токены. Отдельно проверить старый backup v1.
2. Убедиться, что попытка добавить `PostUp = /bin/sh ...` в конфиг с правами панели **отклоняется root-командой**. Не исполнять вредоносную тестовую команду вне изолированного стенда.
3. Проверить no-privilege-escalation границу Unix сокета; `arcvpn` не должен получать произвольный root shell/exec.
4. Проверить право доступа 0600/0700 к конфигам, backup и SQLite; отсутствие секретов в публичном API.
5. На VPS с включённым UFW убедиться, что необходимые UDP/TCP доступны **без обхода политики SSH**; тестировать с двумя SSH-сессиями и out-of-band.
6. Проверить многократное включение/отключение WG/AWG и idempotent удаление NAT/forward правил. Проверить конфликт с существующим nftables/UFW policy; автоматизацию firewall согласовать в этапе 3.

## 5. Что фиксировать

Для каждого пункта: OS/kernel version; версии Xray/Hysteria2/WireGuard/AWG; команда, exit code, timestamp и санитизированный вывод; версия/имя клиента; вид подключения (LTE/Wi-Fi), успешный выходной IP; дефект и исправляющий коммит. Внести результаты в `docs/implementation-status.md`. Без результатов весь этап 2 остаётся `EXTERNAL_PENDING`, не `ACCEPTED`.


## Приложение к 0.4.3

1. CI при отсутствии frontend/package-lock.json создаёт файл временно на сетевом Linux runner и публикует артефакт `arcvpn-frontend-lockfile`. Забрать его, проверить транзитивные версии и закоммитить. Только затем считать frontend dependency graph закреплённым.
2. Для AmneziaWG 3.1 проверить паритет сервер/клиент `RandomTrailers=off`, `DisableCookies=off`, `ContentPaddingAddition=32-128`, `HeaderProtectionKey`. Проверить реальные UDP/MTU и поведение handshake. См. upstream #185 и #186.
3. SHA256 внутри релиза подтверждает отсутствие случайных изменений *относительно manifest*, но не аутентичность источника, если нападающий способен заменить и файлы, и manifest. До production требуются защищённая публикация релиза и проверка происхождения бинарников/тегов.

## Уточнения по 0.4.4

Проверить три новые границы отказа: (1) отказ Hysteria после обновления XHTTP восстанавливает активный Xray, (2) неудачная первоначальная настройка удаляет новый Xray JSON и останавливает Xray, (3) откат после restart не оставляет частично записанный конфигурационный файл. Системная root-команда `stop\n` разрешена только доверенному UID через Unix socket и только для `arcvpn-xray.service`.

Прежде чем начинать полевые испытания, выполнить `scripts/verify-stage2-local.sh`, а затем реальный npm build и браузерный E2E (не ограничиваться успешной проверкой синтаксиса TS). Результаты и найденные дефекты вносить в `docs/implementation-status.md`.
