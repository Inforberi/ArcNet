# Протокол передачи внешних проверок Codex

Документ предназначен для запуска **на отдельном тестовом VPS/VM**, не на рабочем сервере с 3x-ui. Наличие исходного кода и прохождение unit-тестов не являются доказательством production-работоспособности.

## 1. Безопасная подготовка

- Использовать только VPS с консольным доступом через провайдера и доступным snapshot/backup.
- **Никогда** не вставлять SSH-пароли, приватные ключи, одноразовые enrollment-токены, cookies администратора, URL подписок с токенами и содержимое backup в отчёты/чаты.
- Проверить точную ОС, версию, архитектуру и доступность необходимых портов. Снять snapshot; отдельно проверить возможность входа по SSH и через provider console.
- Не выполнять `install.sh` на сервере с действующим 3x-ui, другими VPN или чужими сервисами; проверка конфликтов делается на специальном стенде.
- Перед любыми изменениями firewall, sshd, systemd и TLS показать план команд, сохранить рабочую сессию и подготовить rollback; при отсутствии консольного доступа отложить тест.
- Не обходить TLS (`curl -k`, `insecureSkipVerify`) и не отключать безопасность ради зелёного статуса.

## 2. Универсальный формат отчёта

Создать отдельный Markdown файл в `docs/testing/external-results/YYYY-MM-DD-stage-N.md` (дата фактического теста). Структура:

```md
# ArcVPN / Stage N / внешняя проверка
- Commit: <реальный SHA или контрольная сумма архива>
- Дата и система: <фактические дата, OS/версия, архитектура, systemd>
- Движки/браузеры/клиенты: <точные версии>
- Сценарий и входные условия: <без секретов>
- Команда/действие: <выполненное, не предположительное>
- Ожидание: <проверяемое условие>
- Факт: PASS / FAIL / BLOCKED / NOT RUN
- Доказательство: <санитизированные журналы, скриншоты, exit status>
- Rollback: <что выполнено и что восстановилось>
- Дефекты: <ссылка на задачу либо описание воспроизведения>
- Вывод: ACCEPTED / EXTERNAL_PENDING / FAILED
```

Строки в угловых скобках — поля **отчёта** для фактических данных, не команды и не значения по умолчанию. Нельзя оставлять их заполненными выдуманными фактами.

## 3. Задание Codex: этап 1

**Цель:** выполнить реальные проверки, которые не удалось сделать в исходном чате; при ошибке исправить код и повторно проверить. Не менять проектные требования без согласования. В `docs/ai/current-task.md` отражать фактический результат.

### A. CI/React build (машина с интернетом и Node/npm)

```bash
node --version
npm --version
go version
cd frontend
npm install --package-lock-only --ignore-scripts --no-audit --no-fund
cd ..
# Save frontend/package-lock.json to the repository, review dependencies.
./scripts/build-release.sh
./dist/arcvpn-linux-amd64 frontend-check
python3 tests/react_e2e.py
```

Примечание: первый `npm install --package-lock-only` нужен только для **первого** получения lockfile. После фиксации `frontend/package-lock.json` в репозитории использовать только `npm ci` и проверять неизменность lockfile. При версионированных ограничениях CGO удостовериться, что стоят необходимые dev-библиотеки и gcc; не глушить неудачи скрипта.

Перед E2E на сборочной машине установить `playwright` для Python и Chromium (`python3 -m pip install playwright`, затем `python3 -m playwright install chromium`). Скрипт `tests/react_e2e.py` сам поднимает Go API с **встроенным** React и проверяет браузерные сценарии на локальном HTTP.

### B. Браузерное E2E

Запустить **настоящий** Go API с **реальной** React production сборкой. Для каждого размера окна `320, 390, 768, 1024, 1440` проверить:

- страницу авторизации, вход/выход, 401/500, потерю соединения, перезагрузку;
- таблицы и формы пользователей, модальные окна, QR, ссылку подписки, текст ошибок;
- экран нод и получение одноразовой команды, backup import preview, журналы, темы;
- overflow страницы/таблиц, sticky навигацию, dropdown, focus trap, Escape, переходы клавиатурой;
- одинаковый UI по HTTP тестовому стенду и публичному HTTPS без недопустимых cookie/Origin-ошибок.

Фиксировать скриншоты, браузерные ошибки, ошибочные HTTP-ответы и воспроизводимые шаги. Отдельно проверять отсутствие секретов в браузерных логах.

### C. Один чистый VPS

Проверить snapshot/rescue console, затем установить пакет строго по документации, проверить `systemctl`, права доступа и перезапуск, доверенный HTTPS по IP и обновление сертификата, `xray run -test`, реальное VLESS/Reality-соединение с внешнего клиента. Затем проверить безопасный rollback некорректного Xray config и неизменность SSH после firewall-операций. Не использовать действующую 3x-ui как стенд.

Если `install.sh` не работает, корректировать его и повторять на **новой чистой VM**, а не объявлять состояние зелёным после ручных донастроек. Документировать все дополнительные ручные действия как дефекты установщика.

## 4. Последующие этапы (назначения)

- **Этап 2:** Xray TCP/XHTTP; Hysteria2 QUIC; WireGuard; AmneziaWG: реальные клиенты, QR/config, UDP/TCP fallback, проверка NAT и версия клиента. Сценарии в `docs/features/inbounds-and-protocols.md`.
- **Этап 3:** HTTPS IP renew, sshd/UFW rollback, 2FA, password reset, ротация логов панели/Xray, полное восстановление ArcVPN на другой IP. Сценарии в `docs/features/server-security.md` и `docs/features/backup-and-migration.md`.
- **Этап 4:** два VPS, bootstrap по команде и SSH UI, сертификаты/токены агента, разрыв controller, пробные пользовательские соединения и проверка last-good.
- **Этап 5:** прямой, A→B, B→A, резерв B→C с реальным egress IP, отказ входного IP и отдельные клиентские пробы. Сравнить «сервер видит VPN» и «клиент реально подключается»; не обещать незаметный сбой.
- **Этап 6:** дополнительные протоколы только при подтверждённых серверных и клиентских версиях; выключенные движки не потребляют ресурсы.
- **Этап 7:** одношаговая установка, обновление, rollback, restore, длительные сбои, 1 vCPU/1 ГБ по фиксированному профилю, выпуск проверенного релизного архива.

## 5. Когда Codex завершил проверку

1. Сохранить отчёт в `docs/testing/external-results/`.
2. При FAIL сделать минимальный исправляющий commit и повторить все затронутые тесты.
3. Обновить `docs/implementation-status.md` и `docs/ai/current-task.md`; в `docs/planning/acceptance.md` указать доказательства.
4. Сдать этап только после локальной и внешней проверки; отсутствие доступного стенда = `EXTERNAL_PENDING`, а не `PASS`.
